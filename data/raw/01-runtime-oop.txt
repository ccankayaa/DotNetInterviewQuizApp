runtime~advanced~CIL ve metadata~CIL and metadata~C# derleyicisi CIL talimatları ile tür ve üye metadata'sını assembly içine yazar; CLR bunları yürütme sırasında kullanır.~The C# compiler places CIL instructions and type/member metadata into an assembly; the CLR uses both at execution time.~Üretilen IL'yi ildasm veya ILSpy ile inceleyip kaynak kod varsayımlarını doğrula.~Inspect emitted IL with ildasm or ILSpy before assuming source syntax determines runtime behavior.~CIL'yi işlemcinin doğrudan yürüttüğü yerel makine koduyla karıştırmak hatalı performans yorumuna yol açar.~Confusing CIL with CPU-native machine code causes incorrect performance assumptions.~Taşınabilir CIL ile önceden üretilmiş platforma özel yerel kod farklı dağıtım ve açılış maliyetleri taşır.~Portable CIL and precompiled platform-specific native code have different deployment and startup costs.~Assembly metadata'sı, JIT çıktısı ve call instruction'ları problemi ayrı katmanlarda gösterir.~Assembly metadata, JIT output, and call instructions reveal different execution layers.
runtime~advanced~CLR yükleme ve doğrulama~CLR loading and verification~CLR assembly yükleme, tür sistemi, hata işleme, bellek yönetimi ve JIT çalışma zamanını koordine eder.~The CLR coordinates assembly loading, the type system, exception handling, memory management, and JIT execution.~Sorunu yükleme, JIT, GC veya uygulama kodu katmanında izole ederek teşhis et.~Isolate issues at loading, JIT, GC, or application-code level before tuning.~CLR ile JIT'yi özdeş saymak veya bütün kodun başlangıçta JIT edildiğini varsaymak yanlıştır.~Equating the CLR with the JIT or assuming every method is JIT-compiled at startup is wrong.~Çalışma zamanı servisleri üretkenlik sağlar ancak başlatma ve yönetilen kod maliyetleri ölçülmelidir.~Runtime services improve productivity, but startup and managed execution costs must be measured.~İlk çağrı gecikmesi, assembly load olayları ve runtime trace verisi sorunu ayrıştırır.~First-call latency, assembly-load events, and runtime traces distinguish the issue.
runtime~advanced~JIT ve tiered compilation~JIT and tiered compilation~JIT ihtiyaç oldukça IL'yi native koda çevirir; tiered compilation sıcak metotları sonraki katmanlarda iyileştirebilir.~The JIT compiles IL into native code on demand; tiered compilation can optimize hot methods in later tiers.~Benchmark sırasında ısınma süresini ve tiered PGO etkisini hesaba kat.~Account for warmup and tiered PGO effects during benchmarking.~İlk çağrının süresiyle kararlı durum throughput'unu aynı metrik gibi karşılaştırma.~Do not compare first-call latency and steady-state throughput as one metric.~Hızlı başlangıç kodu ve kararlı durum optimizasyonu arasında farklı öncelikler bulunur.~Quick startup code and steady-state optimization have different priorities.~Warmup sonrası dağılım, JIT event'leri ve sıcak metot CPU profili bilgi verir.~Post-warmup latency distribution, JIT events, and hot-method CPU profiles provide evidence.
runtime~advanced~ReadyToRun ve Native AOT~ReadyToRun and Native AOT~ReadyToRun önceden derlenmiş native bölümler içerirken Native AOT uygulamayı yayımlamada platforma özel koda derler.~ReadyToRun contains precompiled native portions, whereas Native AOT compiles the app to target-specific native code at publish time.~AOT uygunluğu için trim/reflection uyarılarını, dinamik yüklemeyi ve başlangıç profilini denetle.~Audit trim/reflection warnings, dynamic loading, and startup profiles before adopting AOT.~Native AOT'nin sınırsız Reflection.Emit veya runtime assembly yüklemesi desteklediğini varsayma.~Never assume Native AOT supports unrestricted Reflection.Emit or runtime assembly loading.~Başlangıç ve ayak izi avantajı, dinamik özelliklerden ve taşınabilirlikten ödün verebilir.~Startup and footprint gains can restrict dynamic features and portability.~Publish uyarıları, binary boyutu, ilk istek gecikmesi ve AOT uyum testlerini izle.~Track publish warnings, binary size, cold-request latency, and AOT compatibility tests.
runtime~advanced~call ve callvirt IL talimatları~call versus callvirt IL~IL'deki call doğrudan çağrıya, callvirt sanal sevke veya null kontrolü gerektiren çağrıya hizmet edebilir.~In IL, call performs a direct call; callvirt can perform virtual dispatch or enforce a null check.~C# çağrı semantiğini tahmin etmek yerine gerçek IL ve hedef metodun virtual niteliğini incele.~Inspect actual IL and whether the target is virtual instead of guessing from C# syntax.~Her callvirt talimatının çalışma zamanında sanal override seçimi yaptığını düşünme.~Do not assume every callvirt instruction performs virtual override dispatch.~Sanal dispatch genişletilebilirlik sağlarken devirtualization performansı duruma göre değiştirir.~Virtual dispatch provides extensibility while devirtualization can change costs case by case.~JIT disassembly'deki devirtualization ve inline kararlarını benchmark ile karşılaştır.~Compare devirtualization and inlining in JIT disassembly against benchmarks.
runtime~advanced~AssemblyLoadContext~AssemblyLoadContext~AssemblyLoadContext assembly'lerin ayrı çözümleme ve kaldırılabilir yükleme bağlamlarını yönetir.~AssemblyLoadContext manages isolated resolution contexts and potentially unloadable assembly loading.~Plugin mimarisinde collectible context ve referans temizleme yaşam döngüsünü tasarla.~Design collectible contexts and reference cleanup for plugin lifecycles.~Bir nesne veya static referans hayattayken context'in kesinlikle kaldırılacağını varsayma.~Do not assume a context unloads while objects or static references keep it alive.~Plugin izolasyonu bağımlılık sürümlerini ayırır ancak güvenlik sandbox'ı anlamına gelmez.~Plugin isolation separates dependency versions but is not a security sandbox.~WeakReference ile unload doğrulaması ve assembly çözümleme logları kullan.~Use WeakReference-based unload checks and assembly-resolution logs.
runtime~advanced~Reflection ve metadata erişimi~Reflection and metadata access~Reflection, runtime tür metadata'sını okuyarak üyeleri bulmayı ve çağırmayı sağlar; runtime kod üretimi farklı yetenektir.~Reflection inspects runtime type metadata to find and invoke members; runtime code generation is a separate capability.~Yansıtma tabanlı keşfi önbelleğe al, gerekirse source generator ve statik kayda geç.~Cache reflection-based discovery; use source generators or static registration where appropriate.~Gelişigüzel assembly taraması AOT trimming kırılmalarına ve gereksiz sıcak yol maliyetine yol açabilir.~Unrestricted assembly scanning can break under AOT trimming and add avoidable hot-path cost.~Dinamik esneklik tip güvenliği, uygulama başlangıcı ve AOT uyumluluğu ile dengelenir.~Dynamic flexibility trades against type safety, startup cost, and AOT compatibility.~Trimming analyzer uyarıları ve başlangıç allocation'ları riskleri gösterir.~Trimming analyzer warnings and startup allocations expose risks.
runtime~advanced~Boxing ve unboxing~Boxing and unboxing~Boxing değer tipini object veya interface olarak kutular; unboxing uygun tür denetimiyle değeri çıkarır.~Boxing wraps a value type as an object or interface; unboxing extracts the value after a compatible type check.~Sıcak yollarda generic koleksiyon ve arayüz çağrılarının boxing üretip üretmediğini profille.~Profile hot-path generics and interface calls for unexpected boxing allocations.~Değer tiplerinin her zaman stack'te olduğuna veya interface çağrılarının daima allocation yapmadığına inanma.~Do not assume value types always live on the stack or interface calls never allocate.~Soyutlama kullanım kolaylığı sağlar; box edilen değerler GC tahsisini artırabilir.~Abstractions add convenience; boxed values can increase GC allocations.~Allocation profili, IL box opcode'u ve Gen0 frekansı ipucu verir.~Allocation profiles, the IL box opcode, and Gen0 frequency provide clues.
runtime~advanced~Generic specialization~Generic specialization~CLR generic tür bilgisini korur; JIT değer tipi instantiation'ları için ayrı kod üretirken bazı referans tipi biçimlerini paylaşabilir.~The CLR preserves generic type information; JIT can specialize value-type instantiations while sharing some reference-type code.~Performans iddiasını somut T türüyle benchmark et ve generated code'u incele.~Benchmark the actual T type and inspect generated code before claiming performance.~Tüm generic instantiation'ların daima tek bir makine kodunu kullandığını varsayma.~Do not assume every generic instantiation always shares one native implementation.~Özelleştirme hızlı kod sağlayabilir ancak kod boyutunu artırabilir.~Specialization can improve speed but increase code size.~Kod boyutu, generic instantiation sayısı ve sıcak metot performansını izle.~Track code size, generic instantiations, and hot-method performance.
runtime~advanced~GC nesil modeli~Generational garbage collection~.NET GC kısa ömürlü nesnelerin sık olduğu varsayımıyla Gen0, Gen1 ve Gen2 bölgelerini yönetir.~The .NET GC uses Gen0, Gen1, and Gen2 based on the observation that many objects die young.~Önce allocation hızını ve canlı nesne tutulumunu ölç; refleks olarak GC.Collect çağırma.~Measure allocation rate and object retention first; avoid reflexive GC.Collect calls.~Bellek kullanımının yüksek oluşu tek başına sızıntı kanıtı değildir.~High memory use by itself is not proof of a leak.~GC kısa ömürlü nesneleri verimli toplar ancak uzun yaşayan referanslar temizliği geciktirir.~GC efficiently reclaims short-lived objects, but long-lived references delay reclamation.~Gen2 collection, pause time ve retained heap grafiği ile karar ver.~Use Gen2 collections, pause times, and retained-heap graphs for decisions.
runtime~advanced~LOH ve POH~LOH and pinned object heap~Büyük nesneler çoğunlukla LOH'ye; sabitlenmiş uygun nesneler POH'ye ayrılabilir ve heap davranışları farklıdır.~Large objects typically go to the LOH, while eligible pinned allocations can use the POH; their heap behaviors differ.~Büyük buffer'ları tekrar kullan, pinleme ömrünü kısalt ve parçalanmayı profil üzerinden doğrula.~Reuse large buffers, minimize pinning duration, and verify fragmentation through profiling.~85 KB civarı eşiği her platform için değişmez sözleşme sanma; LOH'nin asla compact edilmediğini de varsayma.~Do not treat the roughly 85 KB threshold as an eternal cross-platform contract or assume the LOH can never compact.~Pooling allocation yükünü azaltabilir fakat tutulan bellek ve karmaşıklığı artırır.~Pooling can reduce allocations but increase retained memory and complexity.~LOH size, fragmentation, pinned count ve full GC duraklamalarını incele.~Inspect LOH size, fragmentation, pinned counts, and full GC pauses.
runtime~advanced~Span ve Memory~Span and Memory~Span<T> stack-only ref struct bellek dilimidir; Memory<T> async sınırları boyunca tutulabilen dilimi temsil eder.~Span<T> is a stack-only ref-struct memory view; Memory<T> represents a view that can survive async boundaries.~Kopyasız parsing için Span, async API için Memory kullan; buffer sahipliğini ayrıca tasarla.~Use Span for allocation-free parsing and Memory for async APIs; design buffer ownership separately.~Span'in nesne heap alanında saklanabileceğini veya buffer ömrünü uzattığını düşünme.~Do not assume Span can be stored as a regular heap field or extends a buffer's lifetime.~Kopyadan kaçınmak verimi artırır ama lifetime ve güvenli erişim disiplinini zorlaştırır.~Avoiding copies improves throughput but increases lifetime-management demands.~Allocation sayısı, kopyalama süresi ve memory ownership hatalarını izle.~Track allocation count, copying time, and ownership violations.
runtime~advanced~Unsafe ve interop~Unsafe code and interop~unsafe pointer erişimi managed güvenlik kontrollerinin bir bölümünü aşar; P/Invoke native sınırdan geçer.~Unsafe pointer access bypasses parts of managed safety; P/Invoke crosses into native code.~Marshalling ve ownership sözleşmelerini yazılı hale getir, SafeHandle ile kaynakları sahiplen.~Document marshaling and ownership contracts; use SafeHandle for native resources.~Native handle'ı finalizer olmadan bırakmak veya buffer uzunluğunu yanlış geçirmek ciddi hatalara yol açar.~Leaking native handles or passing incorrect buffer lengths can cause serious failures.~Interop mevcut native kütüphaneleri açar ama bellek güvenliği ve taşınabilirlik maliyeti taşır.~Interop unlocks native libraries at a cost to memory safety and portability.~Native memory trendleri, handle sayıları ve sınırdaki exception'ları incele.~Inspect native-memory trends, handle counts, and boundary exceptions.
runtime~advanced~Finalizer ve IDisposable~Finalizers and IDisposable~IDisposable deterministik kaynak temizliğini sağlar; finalizer nondeterministik son savunmadır.~IDisposable enables deterministic resource release; a finalizer is a nondeterministic last resort.~using veya await using ve gerekli durumlarda SafeHandle ile kaynak ömrünü belirle.~Control resource lifetime with using or await using and SafeHandle when needed.~GC'nin veritabanı bağlantısını veya dosya handle'ını zamanında otomatik kapatacağına güvenme.~Never rely on GC to promptly close database connections or file handles.~Deterministik temizlik daha güvenilir; finalizer eklemek GC maliyetini yükseltebilir.~Deterministic cleanup is more reliable; adding finalizers can increase GC costs.~Açık handle, bağlantı havuzu tüketimi ve finalization kuyruğunu izle.~Monitor open handles, pool exhaustion, and the finalization queue.
